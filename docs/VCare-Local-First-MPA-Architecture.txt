1. EXECUTIVE SUMMARY & NON-NEGOTIABLES
================================================================================

PURPOSE
-------
Deliver a production-grade, local-first Multi-Page Application (MPA) that
replicates the full VCare ERP clinic operations stack without a live server
during demo/field use. All business logic, role chains, maker-checker rules,
and workflow side-effects must behave identically to the current Express +
Prisma application. The architecture must allow a future swap from local
repositories to remote REST/GraphQL APIs with zero UI rewrites.

NON-NEGOTIABLE REQUIREMENTS
---------------------------
  N1.  Every workflow in Section 8 must be implementable and testable E2E.
  N2.  Every multi-role chain in Section 9 must pass acceptance tests with
       role switching (simulated users) without data corruption.
  N3.  Payment collection is ACCOUNTS-only (billing.payments). Bill creation
       may include zero paidAmount for non-Accounts roles.
  N4.  Day close: BM submits (finance.close.submit); Accounts approves/locks
       (finance.close.approve). Maker-checker enforced — submitter ≠ approver.
  N5.  Workflow hooks (follow-ups, audit logs, stock movements, visit creation)
       fire atomically within a single IndexedDB transaction per user action.
  N6.  No raw localStorage for entity data — IndexedDB only. localStorage
       limited to: active session token, UI preferences, last branch, theme.
  N7.  MPA navigation: real URLs (History API), deep-linkable, back-button safe.
  N8.  Parity with smoke-workflow.mjs golden paths is the release gate.

WHAT THIS IS NOT
----------------
  - Not a static site with ad-hoc JSON in localStorage.
  - Not a single-page React app replacing 200+ screens in one bundle.
  - Not a security boundary — client-side RBAC is UX + integrity; real enforcement
    moves to API when backend is connected.

TARGET STACK (RECOMMENDED)
--------------------------
  Build   : Vite + TypeScript
  UI      : Tailwind CSS 4 + existing VCare design tokens
  Pages   : File-based MPA entries (one HTML shell per module area)
  State   : Thin view controllers; domain in services
  DB      : Dexie.js 4.x over IndexedDB (schema versioned migrations)
  PDF     : jsPDF + html2canvas OR pdf-lib for receipts/bills/challans
  Uploads : Blob stores in IndexedDB attachments table
  Test    : Vitest (unit) + Playwright (E2E role chains)
  Deploy  : Netlify / static CDN (assets only; no server functions required)

DEPLOYMENT MODES
----------------
  Mode A — Pure Local (Phase 1 target)
    - Seed on first load from bundled seed.json (mirror prisma/seed.js output)
    - All writes local; export/import JSON for backup
    - Multi-user simulation: quick user switcher (dev/demo) OR separate browser
      profiles per role (production demo)

  Mode B — Hybrid Sync (Phase 3)
    - LocalRepo primary; RemoteRepo push/pull queue
    - Optimistic UI; conflict resolution per entity (Section 16)

  Mode C — Remote Primary (Phase 4)
    - RemoteRepo default; LocalRepo cache for offline read

3. LAYERED ARCHITECTURE
================================================================================

PRESENTATION LAYER
  - Shell: sidebar, top bar, branch selector, role-aware nav, task queue drawer
  - Pages: one route → one page module; lazy-loaded JS per module
  - Components: tables, filters, modals, steppers, toast, confirm dialogs
  - No business rules in templates — only display logic

APPLICATION LAYER (mirrors src/services/*)
  - billingService, pharmacyService, salesOrderService
  - financeClosureService, workflowOrchestrationService
  - taskQueueService, supplyChainOrchestrationService
  - treatmentPlanService, schedulePendingService, kitShortfallService
  - documentPdfService (client PDF generation)
  - Each service: pure async functions; accepts tx context for atomicity

DOMAIN LAYER
  - Entities: typed records matching Prisma models (subset per phase)
  - Value objects: Money (paise integers), BillStatus, DayCloseStatus
  - Domain events: BillCreated, PaymentRecorded, ProcedureCompleted, etc.
  - Invariants enforced here BEFORE persistence

INFRASTRUCTURE LAYER
  - Dexie schema + migrations
  - Repository implementations (CRUD + query indexes)
  - Id generators (billNo, appointmentNo — same sequences as server)
  - Clock abstraction (testable dates for day-close)
  - File/blob store

CROSS-CUTTING
  - authContext: currentUser, permissions Set, branchId
  - auditLog: append-only on every mutating action
  - permissionGuard(route, action): throws ForbiddenError
  - transactionRunner: wraps Dexie transaction + event dispatch

TRANSACTION ATOMICITY PATTERN
-----------------------------
  async function createBillWithWorkflow(input, ctx) {
    return adapter.transaction(async (repos) => {
      const bill = await billingService.createBill(input, repos);
      await workflowEngine.notifyBillWorkflow({ bill, ... }, repos);
      await auditLog.write('BILL_CREATED', bill, ctx.user);
      return bill;
    });
  }

6. WORKFLOW ORCHESTRATION ENGINE
================================================================================

The workflow engine is the nervous system. Each hook mirrors
src/services/workflowOrchestrationService.js and MUST run inside the same
transaction as the triggering mutation.

EVENT → HOOK MAP
----------------
  APPOINTMENT_BOOKED
    → appointment.status = CONFIRMED
    → complete pending follow-ups (NOT_JOINED, REGULAR, TREATMENT)
    → audit log

  CONSULTATION_COMPLETED
    → consultation.status = COMPLETED, consultedAt = now

  PROCEDURE_COMPLETED
    → procedure.status = COMPLETED, completedAt = now
    → linked appointment.status = COMPLETED
    → createVisitFromProcedure
    → maybeCompleteTreatmentSlip
    → scheduleNextSessionFollowUp
    → create follow-up type PROCEDURE_COMPLETED (PENDING)

  BILL_CREATED (via notifyBillWorkflow)
    → link procedure.billId, procedure.status = COMPLETED
    → complete PROCEDURE_COMPLETED follow-ups
    → if balance > 0: create PENDING_ADVANCE follow-up (if not exists)
    → audit log

  PAYMENT_RECORDED
    → if balance <= 0: complete PENDING_ADVANCE follow-ups
    → scheduleRebookAfterPayment

  PHARMACY_BILL_CREATED
    → link procedure.pharmacyBillId
    → audit log

  INDENT_APPROVED (supply chain)
    → fulfillment workflow, stock reservation

  WORK_ORDER_COMPLETED
    → stock inward, cost update

  CLINICAL_CONSUMPTION_RECORDED
    → stockLedger decrement
    → checkReorderAfterConsumption → maybe auto-indent

IMPLEMENTATION
--------------
  class WorkflowEngine {
    constructor(repos, eventBus) {}
    async dispatch(event: DomainEvent, repos): Promise<void>
  }

  // Subscribers registered at app boot — order matters for dependencies

IDEMPOTENCY
  - Hooks check current entity state before writing duplicates
  - followUp creation: findFirst pending of same type before insert

7. ROLE MODEL, RBAC & MAKER-CHECKER MATRIX
================================================================================

STAFF ROLES (9 — no CUSTOMER login, no RECEPTIONIST in v1)
------------------------------------------------------------
  SUPER_ADMIN      level 100   all permissions
  CORPORATE        level 90    executive dashboards, IOU approve, tickets
  BRANCH_MANAGER   level 70    branch ops, bill create (no payment), day close submit
  ACCOUNTS         level 60    payments, refunds, day close approve, finance
  CONSULTANT       level 50    clinical, bill create (no payment)
  THERAPIST        level 45    procedures, consumption, no billing create
  WAREHOUSE        level 40    purchase, GRN, dispatch, stock
  PHARMACIST       level 35    pharmacy bills (no payment at create)
  CALL_CENTER      level 30    leads, appointments, follow-ups

PERMISSION ENFORCEMENT POINTS
-----------------------------
  Route guard       : can user see this page?
  Action guard      : can user submit this form field / button?
  Field guard       : hide paidAmount unless billing.payments
  Service guard     : assertCreatePaymentAllowed(roleCode, paidAmount)
  Maker-checker     : day close, permanent refund, IOU corporate approve

CRITICAL SPLIT PERMISSIONS
--------------------------
  finance.close.submit   → BRANCH_MANAGER
  finance.close.approve  → ACCOUNTS (not BM)
  billing.payments       → ACCOUNTS only
  billing.create         → BM, CONSULTANT (creates bill, balance OK)
  billing.pharmacy       → PHARMACIST
  billing.pharmacy.b2b   → BM, PHARMACIST (no payment at create)
  billing.service.b2b    → BM (no payment at create)
  inventory.authorize    → BM (indents, outward)
  purchase.workorder     → BM authorize, WAREHOUSE fulfill

MAKER-CHECKER RULES
-------------------
  Day Close:
    submitterId stored on submit; approverId on approve; must differ
    lock requires approved status

  Permanent Refund:
    create (BM/Accounts per config) → approve → issueRefund executes

  IOU:
    request (BM) → approve (CORPORATE)

  Petty Cash:
    request → approve (BM)

  Work Order:
    create → PENDING_AUTH → BM authorize → WAREHOUSE complete

  Stock Indent:
    create → PENDING → BM authorize → WAREHOUSE fulfill

8. COMPLETE WORKFLOW CATALOG (MODULE-BY-MODULE)
================================================================================

Each workflow: Trigger → Steps → Actors → Outcome → Side Effects

─── AUTH & SESSION ───────────────────────────────────────────────────────────
  W-AUTH-01  Login
    Trigger: user submits email/password
    Steps: validate → load user+role+permissions → set session
    Outcome: redirect to role home (/portal/{role} or /dashboard)
    E2E: invalid password → error; valid → task queue populated

  W-AUTH-02  Logout
    Steps: clear session → redirect /login

  W-AUTH-03  Branch switch (multi-branch users)
    Steps: update session.branchId → reload branch-scoped data

─── DASHBOARD ────────────────────────────────────────────────────────────────
  W-DASH-01  Role dashboard view
    Permission: dashboard.view (+ module-specific widgets)
    Widgets: inflow, sales, treatment, stock_inward, biometric — per role

─── CUSTOMER / CRM ───────────────────────────────────────────────────────────
  W-CUST-01  Create customer (Call Center, BM)
    Steps: form → validate phone unique → customer.create
    Side: audit log; appears in schedule-pending if no appointment

  W-CUST-02  Customer search & profile
    View: demographics, appointments, bills, treatment slips, follow-ups

  W-CUST-03  Schedule pending workflow
    Steps: multi-step wizard per customer (consultation slot, treatment plan,
           documents, consent prerequisites)
    Actor: Consultant, Therapist, Call Center
    Side: scheduleSteps status updates; task queue "Schedule pending"

  W-CUST-04  Consultation
    Steps: open consultation → notes → complete
    Hook: onConsultationCompleted
    Actor: Consultant

  W-CUST-05  Customer photos / documents
    Permission: customer.photos
    Upload → attachments blob store

  W-CUST-06  Treatment plan / slip
    Create slip → sessions → procedures linked to slip
    Hook: session due dates, next sitting follow-up

  W-CUST-07  Inactive customers report (read-only)

  W-CUST-08  Refund complaints register
    Links to billing.refunds workflow

─── CALL CENTER ──────────────────────────────────────────────────────────────
  W-CC-01  Dialer lookup
    Steps: phone search → customer match/create → book appointment
    Hook: onAppointmentBooked

  W-CC-02  Follow-up queue
    Types: NOT_JOINED, REGULAR, TREATMENT, PROCEDURE_COMPLETED, PENDING_ADVANCE

    Actor: Call Center

  W-CC-03  Treatment booked confirmation
